Introduction

A REST layer bolted onto Odoo specifically for the Shri Hari distributor app — login, catalog, and order placement, all backed by real Odoo records.

Purpose

The shrihari_api module exposes a set of plain HTTP endpoints (Odoo http.Controller routes) that the mobile app calls directly. There is no intermediate API gateway — every call runs straight into Odoo's ORM, sudo()'d past normal user access rights, with its own custom bearer-token auth layer instead of Odoo's web session cookies. A subset of endpoints (§15) additionally act as a transparent proxy to Miracle Cloud ERP itself — the app calls Odoo instead of Miracle directly, and gets Miracle's own response back untouched.

Architecture at a Glance

ConceptDetail
StyleREST-shaped HTTP endpoints (Odoo type='http' controllers, not Odoo's JSON-RPC)
Data FormatRequest: multipart/form-data or application/x-www-form-urlencoded body params. Response: JSON.
AuthenticationCustom Bearer token, issued by /user_login and stored in the partner.api.key model — independent of Odoo's own login sessions
Transport SecurityUse HTTPS in production. Development instances shown here run over plain HTTP on localhost.

API Conventions

Rules that apply across every endpoint below, stated once here.

Every call (except login) needs two things

  • user_id — included as a normal body parameter on every request, not just in the URL.
  • Authorization: Bearer <access_token> — the header, carrying the token returned by /user_login.

Both are checked together by a shared helper before any endpoint's own logic runs. If either is missing or invalid, you get a success: false response before any business logic executes — see 16 Error Reference.

Standard Response Shape

Every response carries a top-level success boolean. Beyond that, the shape is endpoint-specific — some nest results under data, others use a bespoke key (categories, products, sale_orders...). There is currently no single fixed envelope across all endpoints — always check each endpoint's own example below rather than assuming a common shape.

MINIMUM SHAPE — EVERY RESPONSE
{  "success": true,  // or false  "message": "..."  // present mainly on errors, and on a few success cases  // ...remaining fields vary per endpoint}

Image URLs

Wherever a response includes image_url, it's an absolute link into Odoo's built-in attachment controller, e.g. /web/image/product.template/<id>/image_1920, with a ?t=<timestamp> cache-buster appended. No separate download endpoint or auth is needed to load it — the image controller is public.

Numeric & ID Conventions

FieldMeaning
user_idAn Odoo res.users id — this is what the app must send back on every call, not the partner/contact id.
sale_capture_idLegacy name kept for app compatibility — it is the real sale.order id, not a separate model.
product id (catalog)The product.product (variant) id, not the product.template id — use this when placing an order.

Number Formatting

Every monetary/quantity value (prices, rates, quantities, totals) is returned as a string, formatted dynamically: 2 decimal places when the value is a whole number, 4 decimal places when it actually carries a fractional part.

EXAMPLES
2376 → "2376.00"   // whole number → 2 decimals2185.92 → "2185.9200"  // has a fraction → 4 decimals
These are strings, not JSON numbers
Parse every such field as a number on your side before doing math or comparisons with it — don't compare it as text. id fields are the exception: those stay real JSON integers.

Environments & Prerequisites

BASEhttps://shreehari.applified.co.in/

Before the app can do anything useful

  1. The customer must have an active res.users account linked to a res.partner (see the "Grant App Access" wizard on any Contact).
  2. shrihari_api, shrihari_sales, and app_miracle_account must be installed on that user's company.
  3. A single app.version record must exist for 6 Get App Version to return anything.
  4. Settings → Sales: set Mobile App Global Pricelist if you want tiered slab pricing, and Mobile App Freight & Transport Charge if freight should be auto-added to orders.
4

Quick Start

  1. Call POST /user_login with mobile/email + password. Store the returned user_id and access_token.
  2. Attach user_id as a body param and Authorization: Bearer <access_token> as a header on every call from here on.
  3. Browse the catalog: POST /product_category, then POST /products_by_category per category.
  4. Place an order: POST /create_sale_capture. Odoo confirms it, ships it, and invoices it automatically.
  5. Before the token's 7-day expiry, call POST /refresh_token to extend it — otherwise the user has to log in again.

Authentication

Custom bearer tokens, independent of Odoo's own login. Two endpoints: get one, and keep it alive.

Login

POST/user_login

Request Parameters

ParameterTypeRequiredRemarks
emailStringOne of email/mobileMatched against res.users.login.
mobileStringOne of email/mobileMatched by last 10 digits — country-code prefixes (e.g. +91) are tolerated automatically.
passwordStringYesChecked via Odoo's own credential check.
device_tokenStringNoPush-notification device token; stored/updated on the user record on every login.

Success Response

200 OK
{  "success": true,  "message": "Login Successful!",  "user_id": 42,  "name": "Ramesh Traders",  "access_token": "9f2c...(64 hex chars)",  "customer": {    "partner_id": 108, "miracle_account_id": "AC0234",    "mobile": "9998887770", "credit_limit": "100000.00", "crdays": 30    // ...street/city/state/country/email  }}

Error Responses

MessageCause
Email or Mobile, and password are required!Neither identifier supplied.
Account not found!No matching, active user.
Account deactivated, please contact support!A matching user exists but is archived.
Invalid password!Credential check failed.
Token reuse
An existing, unexpired token for the same user is reused rather than minting a new one — logging in twice does not invalidate the first session.

Refresh Token

POST/refresh_token

Identifies the user purely from the Authorization header — no user_id body param needed here. Extends expiry by 7 days from now.

200 OK
{  "success": true,  "message": "Token expiry extended successfully",  "user_id": 42, "user_name": "Ramesh Traders",  "new_expiry_date": "2026-09-23 10:15:00"}
Call this proactively
There is no automatic refresh anywhere in the system. If the app never calls this, the token silently stops working after 7 days and every endpoint starts returning "Token is Expired".

Account

Deactivate Account

GET/delete_account/{user_id}

user_id is a URL path segment here, not a body param.

No authentication on this endpoint
Unlike every other endpoint in this guide, /delete_account does not check a Bearer token or verify the caller owns the account being deactivated — any caller who knows a user_id can deactivate it. Do not expose this route to anything other than a trusted, authenticated in-app "delete my account" action; it should not be called with a user-supplied id from outside that flow.
200 OK
{ "success": true, "message": "User deactivated successfully!", "user_id": 42, "login": "9998887770" }
Reserved account
user_id = 7 always returns a success message but is never actually archived — it's an internal safeguard, not a bug in your integration.

Products

POST/products_by_category

Request Parameters

ParameterRequiredRemarks
user_idYesStandard auth param.
category_idNoIncludes products in child categories automatically. If omitted, all products are returned.

Success Response

200 OK
{  "success": true, "category_id": 9, "category_name": "SETWET", "total_products": 1,  "products": [ {    "id": 4252 // product.product id — use this to place an order,    "name": "SETWET 50/-(72) BLUE.", "default_code": "",    "list_price": "2376.00", "miracle_cart_rate": "33.00", "miracle_mrp": "50.00",    "taxes": [ { "id": 5, "name": "18% GST S" } ],    "free_qty": "0.00", "best_company": "Shree Hari Marketing",    "uom": "UOM QTY2 72.0000", "uom_qty": "72.00", "category": "SETWET",    "pricing_slabs": [      { "min_qty": "25.00", "price": "2304.00", "discount_type": "fixed",        "single_piece_price": "32.00", "discount_percent": null,        "discount_message": "Buy 25+ at ₹2304.0/box" },      { "min_qty": "100.00", "price": "3420.00", "discount_type": "percentage",        "single_piece_price": "50.00", "discount_percent": "5.00",        "discount_message": "Buy 100+ at ₹3420.0/box" }    ],    "image_url": "https://.../web/image/product.template/.../image_1920?t=..."  } ]}
free_qty vs list_price
free_qty is on-hand minus reserved stock for the user's company — treat it as the sellable cap for that line. pricing_slabs is only populated when Mobile App Global Pricelist is configured in Settings; otherwise it's always an empty array.
uom vs uom_qty
uom is the human-readable UOM name (e.g. "UOM QTY2 72.0000"); uom_qty is the actual pack size as a number (72) — use this one for any math, no string-parsing needed.
How each pricing_slabs entry is priced
discount_type: "fixed" rules are entered in Odoo as a per-piece rate — single_piece_price is that rate, and price is it multiplied by uom_qty (the box price actually charged).
discount_type: "percentage" rules discount off Miracle MRP (single_piece_price here is the MRP), not off list_price — since MRP is usually well above the normal selling rate, a percentage slab can legitimately price higher than the plain box price. This is intentional, not a bug — display it as its own tier, not as automatically "cheaper."
Both numbers come from the exact same calculation Odoo uses to actually charge a real order, so price here is always what the customer will be billed if that quantity is ordered.

Create Order

POST/create_sale_capture

One call does everything: creates the order against the logged-in user's own contact, confirms it, validates the delivery, creates and posts the invoice, and queues a background sync to Miracle Cloud ERP.

Request Parameters

ParameterTypeRequiredRemarks
user_idIntegerYesStandard auth param.
line_product_id[0..n]IntegerYesIndexed from 0, contiguous. The product.product id from §8.
line_qty[0..n]FloatYesMust not exceed the product's current free_qty.
line_price[0..n]FloatNoOmit to auto-price from the configured pricelist, or the product's list price if none is set.
Indexed array format
Lines are read as separate form fields line_product_id[0], line_qty[0], line_price[0], then [1], [2]... — reading stops at the first missing index, so indexes must be contiguous starting from 0.

Success Response

200 OK
{  "success": true, "message": "Order created successfully",  "customer_id": 108, "customer_name": "Ramesh Traders",  "sale_capture_id": 331, "reference": "S00331", "state": "sale",  "sale_orders": [ { "id": 331, "name": "S00331", "company": "Shree Hari Marketing", "amount_total": "37485.00" } ]}

Error Responses

MessageCause
Invalid qty/price at line {n}Non-numeric qty/price.
Invalid product_id: {id}Product id doesn't exist.
Not enough stock for product {name}. Available: X, Requested: YRequested qty exceeds free stock.
At least one product is requiredNo valid lines parsed.
Freight & Transport Charges
Odoo automatically appends a freight line to every order — app or backend — priced at (total units across all lines) × (freight product's Sales Price), using whatever product is set under Settings → Sales → Mobile App Freight & Transport Charge. This line will appear in amount_total and in the order lines returned by §10–12; there's nothing the app needs to send for it.
Miracle sync is asynchronous
The response returns as soon as the order/invoice exist in Odoo. The push to Miracle Cloud ERP happens in a background job triggered right after — a success: true here does not guarantee the order has reached Miracle yet.

POST/get_miracle_credentials

Hands the app what it needs to talk to Miracle Cloud ERP directly for the logged-in user's company.

ParameterRequiredRemarks
user_idYesStandard auth param.
200 OK
{ "success": true, "data": [ {  "id": 1, "name": "Shree Hari Marketing",  "MIRACLE_BASE_URL": "https://tpaapi.miracleclouderp.com",  "URL_KEY": "...", "CLIENT_ID": "...", "API_KEY": "...",  "ACCID": "AC0234",  "ACTIVE_TOKEN": "eyJhbGciOiJIUzI1Ni...",  "TOKEN_GENERATED_AT": "2026-09-16 16:22:23",  "TOKEN_EXPIRY_AT": "2026-09-17 16:22:23"} ] }
Largely superseded by §15
This endpoint still works, but as of §15's proxy endpoints, the app no longer needs ACTIVE_TOKEN/CLIENT_ID/API_KEY for account balance, account details, ledger, voucher list, or PDF generation — those now go through Odoo directly. Miracle Account Proxy

The app no longer calls Miracle Cloud ERP directly for these five calls — Odoo makes the Miracle call on your behalf and hands back Miracle's own response, untouched.

Two rules that apply to every endpoint below — not repeated per endpoint
1. Response shape is Miracle's, not this API's usual shape. A successful call returns exactly what Miracle Cloud ERP itself returned — same field names, same nesting, same "IsError": false. Nothing is renamed or reshaped. If Miracle rejects the call, that error is relayed exactly as Miracle sent it too: {"IsError": true, "ErrorCode": "...", "Message": "..."}. Only the very first check — is the Bearer token itself valid — still uses this API's normal {"success": false, "message": "..."} shape, since that's Odoo's own gate, not Miracle's.

2. miracle_account_id is trusted as sent, not cross-checked. Every endpoint below requires it as a parameter — the same value returned in customer.miracle_account_id at §5 Login. Odoo does not verify it belongs to the logged-in user — whatever value the app sends is what gets queried on Miracle. Always send the value that belongs to the currently logged-in user; this is a known, deliberate trade-off, not an oversight.

Generate File

POST/generate_file

One endpoint, three report types, selected by rptType — matches how Miracle itself structures this call.

ParameterRequiredRemarks
user_idYesStandard auth param.
miracle_account_idRPT001 / RPT002Used as uniqueId for these two. Not used for RPT003.
rptTypeYesRPT001 (account statement), RPT002 (ageing/outstanding), or RPT003 (voucher/invoice print).
fromDate / toDateRPT001 onlyYYYY-MM-DD.
reportDateRPT002 onlyYYYY-MM-DD, as-on date.
voucher_idRPT003 onlyA vouid from §14's voucher list — used as uniqueId instead of the account id for this report type.
200 OK — Miracle's own response, untouched
{ "DataModel": "JVBERi0xLjQNCiWio4...(base64 PDF, truncated)...", "IsError": false }
DataModel here is a plain string, not an object
Miracle's own published API guide documents this response as {"DataModel": {"fileName": "...", "pdfBase64": "..."}} — a nested object. What Miracle actually returns in practice is DataModel as the base64 PDF content directly, with no fileName/pdfBase64 wrapper (confirmed by testing). This is a documentation/reality mismatch on Miracle's side, not something Odoo changed — build against response.DataModel as the string itself, not response.DataModel.pdfBase64.
voucher_id is trusted, same as miracle_account_id
RPT003 doesn't verify the requested voucher actually belongs to the calling account — same accepted trade-off as rule 2 above, extended to voucher ids for this one report type.

Error Reference

These checks run before any endpoint's own logic, so they can come back from any route in this guide — except the five §15 Miracle Account Proxy endpoints, where only this table's checks use this shape; everything past that point on those five uses Miracle's own {IsError, ErrorCode, Message} shape instead.

MessageCauseFix
user_id (user_id) is requireduser_id missing from the request body.Always send it, even though it's also implied by the token.
Missing or invalid token formatNo Authorization header, or it doesn't start with Bearer .Set the header exactly as Authorization: Bearer <token>.
Token is ExpiredNo matching, unexpired partner.api.key for that user_id + token pair.Call 5 Refresh Token, or re-login if it's been unused for 7+ days.
HTTP status codes
Most error responses still return HTTP 200 with success: false in the body — check success, not the HTTP status code, to detect failure.
